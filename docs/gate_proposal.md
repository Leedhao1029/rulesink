> **版本**：v1.0  
> **生效日期**：2026-05-15  
> **宪法依据**：SOUL.md v3.3 第三条核心原则"门禁提案机制"  
> **审计**：Soul Arbiter PASS（2026-05-15）

---

## 1. 背景

### 1.1 问题：约束工具的递归困境

约束工具的执行者无法反过来约束工具本身：

```
AI（通过 terminal 执行）
    ↑
    └── L1 越级防治铁律（约束编排层）
            ↑
            └── 铁律本身由 AI 执行
```

铁律无法渗透到工具层（`terminal`/`execute_code`），因为约束工具的行为本身也在工具层执行。

### 1.2 解法：用户作为门禁

用户本人是门禁，绕开了递归困境。AI 只做提议，用户做最终决策，没有任何绕过空间。

---

## 2. 强制执行规则

> **所有任务无例外。** 即日起所有 `terminal`/`execute_code` 调用必须先提案，不允许跳过。

### 2.1 触发条件

任何以下操作之前**必须**提案：

- `terminal()` 调用（bash/命令执行）
- `execute_code()` 调用（Python 脚本执行）
- `patch()` 调用（文件修改，**已通过铁律1/2的绕过场景除外**）

> **注**：通过 `orchestrate()` → L2编排器 → L3脚本 的链路不需要单独提案（铁律1/2已覆盖）。

### 2.2 提案格式

```
[执行提案]
任务：<任务摘要，1句话>
域：<识别的L2域，如it/investment/construction等>
建议：走L1→L2链路（路由到<编排器名称>）
理由：<为什么应该走编排器，1句话>
选项：
  [A] 直接执行（需用户确认绕过编排器）
  [B] 走L1→L2链路

⏱ 超时阈值（与复杂度挂钩）：
   · 复杂度 < 3（简单任务）：10秒
   · 复杂度 3-6（标准任务）：30秒
   · 复杂度 ≥ 7（全角色调度）：无超时，必须等待用户明确输入
   — 超时无响应则执行对应阈值的默认选项B
```

### 2.3 约束

| 约束 | 说明 |
|------|------|
| **选项A永远不是默认** | 提案格式中 B 必须在 A 之前；超时默认 B |
| **超时与复杂度挂钩** | 简单任务10秒、标准任务30秒、全角色调度无超时 |
| **超时执行B** | 对应阈值内无任何响应，执行默认选项B |
| **全角色调度无超时** | 复杂度≥7时必须等待用户明确输入，不自动执行 |
| **用户主动选A才允许A** | 用户必须明确输入 A 才算授权直接执行 |
| **无例外条款** | 所有 terminal/execute_code/patch 调用均需提案，无豁免条件 |

## 3. 提案决策树

```
准备执行 terminal/execute_code/patch
    │
    ├─ 已在 orchestrate() 链路内（铁律1/2已覆盖）
    │   └─ 不需要单独提案，继续执行
    │
    └─ 铁律1/2 覆盖范围外
        │
        ├─ 是 → 生成提案，等待用户响应
        │   ├─ 用户选 A → 直接执行（仅此时允许）
        │   ├─ 用户选 B → 路由到对应 L2 编排器
        │   └─ 30秒超时 → 执行默认 B
        │
        └─ 否（不在触发范围）
            └─ 直接执行
```
